# 分阶段工作流

## 入口选择

新项目先完成 PRD 和代表性原型；接手项目先对照已有材料、源码和最新报告列差距；修复任务先复现并记录当前范围。不要因资料较多就忽略用户最新限制。

## 1. 从想法到 PRD

输入：目标用户、痛点、主要场景、已有材料、预算/时间/平台约束。

执行：
1. 用一句话定义价值；确定核心用户角色、权限边界和成功标准。
2. 拆分 P0/P1/P2 与非目标。确认首期到底包含哪些优先级，不自行扩大范围。
3. 将功能写成“触发—操作—状态—结果”；补齐拒绝、取消、断网、重复操作、过期和权限不足。
4. 明确登录能力、业务时区、数据归属、可见范围、保存策略等会影响实现的选择。
5. 分配验收编号并建立追踪表，记录待确认项。

产物：PRD、页面/角色清单、验收矩阵。退出条件：核心范围与高影响规则已确认；待决项不会阻挡下一阶段。

## 2. 从 PRD 到 HTML 原型

输入：已确认 PRD、页面清单、品牌素材和导航约束。

执行：先画页面与返回关系，再实现可点击原型。提供正常、空态、加载、输入错误、请求失败、无权限等适用状态；模拟状态必须明确标注。让用户走通关键任务并确认代表页，再扩展其余页面。

产物：可本地打开的 HTML 原型与状态说明。退出条件：核心路径没有死路，保存/取消/返回的结果清楚，用户已经确认当前方向。

## 3. 从原型到视觉规范

输入：确认原型、现有设计规范、素材权限。

执行：
1. 已有页面先用 `audit` 或 `product-design:audit` 捕获逐屏证据，记录严重程度、修改措施和截图限制；从零项目先审查可点击原型，不编造运行页面证据。
2. 用 `ui-ux-pro-max` 结合 PRD 和审查结果形成改版方案，先确认代表页及必要错误态。
3. 用 `design-system` 建立三层令牌：基础色值/字号 → 语义用途 → 组件参数。
4. 用 `ui-styling` 把令牌和组件状态转换为原生 WXSS 规则；React、Tailwind 示例不改变微信项目技术栈。
5. 有明确视觉目标后用 `image-to-code` 或 `product-design:image-to-code` 按稿实现；缺少 Skill 时按内置方法回退并记录。
6. 设计正常、按压、处理中、禁用、成功、错误状态；错误贴近字段，失败保留输入。
7. 检查 320/375/430px 与 1/1.3/1.6 倍字号，使用可读文本表达数据；图形不能成为唯一信息源。
8. 导出明确尺寸的素材，登记来源、用途与授权。

产物：DESIGN.md、页面审查记录、高保真 HTML 与状态稿、素材清单、设计 QA 记录。退出条件：代表页确认，组件和状态齐全，设计可以转换成原生实现。

## 4. 从契约到真实业务

输入：PRD、视觉基准、技术栈与当前仓库。

执行：
1. 检查现有结构及工作区；保留已有变更，按任务需要隔离开发。
2. 对齐接口、共享类型、错误模型、鉴权与授权，生成或维护 OpenAPI。
3. 将开发库/测试库放入不同服务或独立目标，绑定本地端口、启用健康检查和持久化。
4. 创建迁移和虚构种子；数据有唯一性/并发约束时落实到数据库及事务。
5. 先打通一个业务闭环，再复用组件和服务扩展。不要长期让前端假数据掩盖接口缺失。
6. 隔离微信外部能力。服务器保管 AppSecret；客户端不持有后端密钥。
7. 检查页面隐藏/销毁清理，错误恢复、草稿隔离和请求过期行为。

产物：前后端源码、迁移、示例环境配置、开发规范。退出条件：关键路径在真实本地服务和数据库上成立。

## 5. 从检查到验收证据

按照 testing.md 分层验证。只使用与当前源码对应的结果。错误修复后重测相关路径及必要回归；不要为了数字好看重复或扩大无关测试。

产物：TESTING.md、按需求映射的结果、脱敏日志/截图、未执行项。退出条件：当前范围的阻断问题解决，剩余限制可见。

## 6. 从候选构建到体验版

按照 release.md 核验。需要真机连接服务器时先准备可访问的 HTTPS API；本机 localhost 不能默认被手机访问。先验证前后端兼容，再构建并上传候选包。

产物：候选版本清单、上传结果、平台版本状态、体验入口及真机反馈。提交审核与正式发布是后续独立动作。

## 变更处理

用变更记录说明“原规则 → 新规则 → 影响的页面/接口/测试”。处理文档与实现冲突时查明时间和确认依据；不要抹掉仍有效的用户约束。局部修复允许只更新相关章节，不要求六阶段从头重做。
